# Personal Task List User Stories

## Story Map

These stories define the work needed to complete the Personal Task List challenge using Spec-Driven Development.

The stories are ordered by priority. We should complete them in this order because each step creates the contract or foundation for the next one.

| Order | Jira Ticket Type | Title | Priority | Outcome |
| --- | --- | --- | --- | --- |
| 1 | Story | Define the API vision and scope | Highest | Product scope is clear before implementation. |
| 2 | Story | Define the task data model | Highest | The data structure is documented before coding. |
| 3 | Story | Define the OpenAPI contract | Highest | The API contract is locked before implementation. |
| 4 | Story | Create the ASP.NET Core Web API solution | High | The project structure exists. |
| 5 | Story | Configure SQLite persistence with EF Core | High | The API can persist tasks in SQLite. |
| 6 | Story | Create a task | High | Users can add tasks to the list. |
| 7 | Story | View the task list | High | Users can retrieve existing tasks. |
| 8 | Story | Edit a task | Medium | Users can update task details. |
| 9 | Story | Mark a task as completed | Medium | Users can complete tasks. |
| 10 | Story | Delete a task | Medium | Users can remove tasks. |
| 11 | Story | Verify implementation against the specification | High | Tests prove the API follows the spec. |

## API Decision

Version 1 will use five endpoints:

| Method | Endpoint | Story |
| --- | --- | --- |
| `POST` | `/api/tasks` | Create a task |
| `GET` | `/api/tasks` | View the task list |
| `PUT` | `/api/tasks/{id}` | Edit a task |
| `PATCH` | `/api/tasks/{id}/complete` | Mark a task as completed |
| `DELETE` | `/api/tasks/{id}` | Delete a task |

`GET /api/tasks/{id}` is not included in version 1. The challenge requires a task list, not a task detail view.

## Story 2: Define The Task Data Model

**Jira title:** Define the task data model

**As a** developer implementing the API,  
**I want** a documented task data model,  
**So that** the database schema and API payloads are consistent.

### Description

Create `docs/data-model.md` with the `Task` entity, field definitions, validation rules, and a PlantUML diagram if useful.

The model should stay minimal. It should not introduce users, projects, categories, due dates, or priorities.

### Proposed Fields

| Field | Type | Required | Notes |
| --- | --- | --- | --- |
| `id` | `Guid` | Yes | Unique task identifier generated by the API. |
| `title` | `string` | Yes | Required task title. |
| `description` | `string?` | No | Optional task details. |
| `isCompleted` | `bool` | Yes | Defaults to `false`. |
| `createdAt` | `DateTimeOffset` | Yes | Set when the task is created. |
| `updatedAt` | `DateTimeOffset` | Yes | Set when the task is created or changed. |
| `completedAt` | `DateTimeOffset?` | No | Set when the task is completed. |

### Acceptance Criteria

```gherkin
Scenario: Data model document defines Task
  Given the repository contains a docs folder
  When I open docs/data-model.md
  Then the document defines a Task entity
  And it lists each field name
  And it lists each field type
  And it identifies required and optional fields
```

```gherkin
Scenario: Data model remains minimal
  Given the challenge is for a personal task list
  When I review the data model
  Then it does not include users
  And it does not include authentication fields
  And it does not include categories, priorities, reminders, or due dates
```

### Definition Of Done

- `docs/data-model.md` exists.
- The `Task` entity is fully documented.
- The model can be implemented directly with Entity Framework Core.

## Story 6: Create A Task

**Jira title:** Create a task

**As a** user,  
**I want** to create a task,  
**So that** I can track something I need to complete.

### API Contract

`POST /api/tasks`

### Request Body

```json
{
  "title": "Buy groceries",
  "description": "Milk, eggs, bread"
}
```

### Acceptance Criteria

```gherkin
Scenario: Create task with valid data
  Given the API is running
  When I send a POST request to /api/tasks with a valid title and optional description
  Then the API returns 201 Created
  And the response contains the created task
  And the task has a generated id
  And isCompleted is false
  And createdAt is set
  And updatedAt is set
  And completedAt is null
```

```gherkin
Scenario: Create task without title
  Given the API is running
  When I send a POST request to /api/tasks without a title
  Then the API returns 400 Bad Request
  And no task is created
```

```gherkin
Scenario: Create task with blank title
  Given the API is running
  When I send a POST request to /api/tasks with a blank title
  Then the API returns 400 Bad Request
  And no task is created
```

### Definition Of Done

- Endpoint is implemented according to `docs/openapi.yaml`.
- Valid create requests are persisted in SQLite.
- Invalid create requests return `400 Bad Request`.
- Tests cover valid and invalid creation.
